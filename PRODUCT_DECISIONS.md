# Tusk.ai — Product Decisions and Open Questions

Use this file to record durable decisions. Add a date, context, decision, consequences, and status for each decision. Significant technical choices also need an ADR in `docs/adr/`.

## Confirmed baseline decisions

1. Product name is exactly `Tusk.ai`.
2. Product branding and customer-facing copy remain independent of competitions, events, sponsors, and judging.
3. The first product experience is an Android app, backed by reusable server-side capabilities.
4. Mission Mode is the core differentiator: goal → plan → approved execution → verified results.
5. No SMS or phone-call integrations in the initial MVP.
6. Never fake AI execution, progress, tool results, delivery, or success.
7. Keep provider secrets and privileged credentials on the backend.
8. Require explicit approval for consequential external actions.
9. Start with one orchestrator and modular tool adapters; add multiple agents only when justified.
10. Deliver in incremental, testable phases.
11. Use a premium monochrome design system: black, white, and neutral greys only, with light/dark themes.
12. Never use emojis in product UI or app-authored sample/demo content; use professional vector icons.
13. Design a complete, low-friction first-run journey inspired by familiar conversational AI onboarding, without copying another product’s branding or exact interface.
14. Authentication methods must be real and configured; Google sign-in is optional and must not be presented as functional until integrated and tested.

## Open questions to resolve in Phase 0

- Which Android stack best fits the installed environment and desired APK reliability?
- Which backend stack is simplest to maintain and deploy?
- Which text and image providers are available, permitted, and affordable?
- Which persistence and object-storage services fit the MVP?
- Which authentication method should be implemented first, and can a safe guest-first experience be supported?
- Which secure session-storage and account deletion approach fits the selected Android/backend stack?
- Which hosting environment and region should be used?
- Which specific external agent protocol/platform adapter is required, and what are its current SDK requirements?
- What is the initial repeated-use case to validate with real users?
- What retention and deletion controls are needed before public launch?

## Decision Log

### 2026-10-16 — Phase 2: Core Mission UX & Local Planner Adapter Isolation
- Status: Accepted
- Context: Core mission flow needed on-device UX modeling (intake → clarifying questions → structured plan → plan review & approval → mission tracking) prior to Phase 3 real backend connectivity.
- Decision:
  1. Implemented `Mission` & `MissionStep` models with strict state machine validation enforcing allowed transitions: `draft` → `needsClarification` → `readyForApproval` → `approved` → `running` → `completed` / `failed` / `cancelled`, with `failed` → `readyForApproval` retry path.
  2. Isolated `LocalPlannerAdapter` in `app/lib/features/mission/services/local_planner.dart` as a clearly labelled rule-based local generator. All plan review UI explicitly displays a `DEVELOPMENT ADAPTER` badge stating "Plan generated by local development adapter (rule-based planner) — not an AI service."
  3. Stored missions in `MissionRepository` backed by `SharedPreferences`, decoupling conversation deletion (`detachConversation`) so that deleting a chat thread preserves mission records for user review.
  4. Maintained strictly monochrome design (black, white, greys), zero emojis, Lucide vector icons, and honest voice feedback.
- Consequences: UI cleanly unblocks full user flow testing while remaining completely honest; zero technical debt for Phase 3 backend swap.

### 2026-10-19 — Phase 2.5: Backend Runtime Decision (FastAPI/Python 3.12 Confirmed) & Repository Baseline
- Status: Accepted
- Context: `README.md` specified a FastAPI/Python backend target, but the host environment initially lacked Python (only Windows Store stub). Evaluated alternatives (Node.js, Dart, Python).
- Decision:
  1. Confirmed and retained FastAPI/Python as the authoritative backend stack. Python is the native SDK runtime for planned Fetch.ai interoperability (`uagents` in Phase 5) and offers strict Pydantic schema validation matching `API_CONTRACT.md`.
  2. Installed and verified Python 3.12.10 (64-bit) with pip 25.0.1 on the host environment via Windows Package Manager (`winget`).
  3. Initialized local Git version control, configured root `.gitignore` excluding build outputs/large APK binaries/secrets, and created the baseline commit for working Phase 2 code.
  4. Updated `DEVELOPMENT.md` with verified environment versions and commands.
- Consequences: Environment is unblocked for Phase 3 without architecture drift or tech stack rework.
